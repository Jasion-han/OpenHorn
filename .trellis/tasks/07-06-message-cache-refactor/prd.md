# 桌面端消息缓存重构：消除「双写镜像」泄漏与开销

> 状态：待你审阅
> 范围：只做根因（不改消息去重 #1、不改 thinking 语义 #5）
> 影响文件：`apps/desktop/src/stores/chatStore.ts`（几乎全部改动集中在这一个文件）

---

## 一、这件事要解决什么（大白话版）

桌面端聊天有一个隐藏的设计问题：**同一份消息数据，被存了两份，每次更新都要手动改两遍。**

- 第一份：`state.messages` —— 当前屏幕上正在显示的消息（React 用它渲染）。
- 第二份：`messageCache` —— 一个"备份仓库"，你切到别的会话时，把上一个会话的消息暂存进去，切回来时不用重新加载、也不会丢掉正在流式输出的内容。

问题在于：**这两份数据靠"人肉同步"。** 代码里凡是改消息的地方（追加一个流式字符、改一条消息、标记完成……），都要写两遍——先改 `state.messages`，再改 `messageCache`。这带来两个真实的毛病：

### 毛病 A：备份仓库只进不出，内存越用越多（内存泄漏）
`messageCache` 这个"仓库"从创建到现在，**只有存入、没有任何清理逻辑**。你每切换一个会话，就往里塞一整个会话的所有消息。用得越久，仓库越大，占的内存只涨不降。
更糟的是：连"清空聊天状态"的 `reset()` 函数都清不掉它——因为这个仓库是个闭包内部变量，不在能被重置的状态里。

**后果**：桌面端是长期开着的程序，重度使用一整天、切换几百个会话后，内存持续膨胀，最终表现为整个应用变卡、变慢。

### 毛病 B：每输出一个字，都要把消息列表重建两遍（流式性能）
AI 回复是一个字一个字"流"出来的。每来一个字（一个 token），现在的代码会：
1. 把当前会话的**整个消息数组**重新构建一遍（更新 `state.messages`）；
2. 紧接着，**遍历"备份仓库"里的所有会话**，找到这条消息，再把那个会话的**整个消息数组**重新构建一遍（更新 `messageCache`）。

也就是说，**每一个字都要做两次全量重建，外加一次跨会话的地毯式搜索。** 会话越多、消息越长，越慢。

> 这一点很关键：最近几次提交都在优化"代码块高亮"的性能，但那是**表面**。AI 边流式输出边卡顿的**真正根源**，是状态层每个字都在做双倍的全量重建。高亮只是压垮骆驼的最后一根稻草，不是骆驼本身。

---

## 二、根因（第一性原理）

上面两个毛病，**不是两个独立的 bug，是同一个设计决策的两个症状**：

> **`messageCache` 缓存了"所有切换过的会话"的"全部消息"，并且和 `state.messages` 靠每次手动双写来保持一致。**

顺着这个根因反问一句：**这个备份仓库，真的需要存"所有会话的全部消息"吗？**

不需要。它存在的唯一理由（代码注释自己写的）是：**当一个会话正在流式输出时，如果你临时切走再切回，不要丢掉这期间流进来的内容。**

- 你切走一个**已经输出完、静止的**会话时——它的消息 DB 里都有，切回来重新加载即可，根本不需要缓存。
- 真正需要"切走后仍能继续写入"的，**只有当前正在跑的那一个 run 所属的那一个会话**。

所以正确的解法不是"给仓库加个容量上限"（那是治标，仍然在维护一个不该那么大的仓库），而是**从根上收窄这个仓库的职责**。

---

## 三、目标

1. **消除内存泄漏**：`messageCache` 不再无限增长，且能被正常清理。
2. **消除流式双倍开销**：流式输出时，不再对"非活跃会话"做扫描和重建。
3. **行为完全不变**：用户视角下，会话切换、流式显示、切走切回不丢内容——这些体验和现在**一模一样**。这是一次纯内部重构，不改任何用户可见行为。

---

## 四、具体怎么改

核心思路一句话：**把"缓存所有会话的全部消息"改成"只缓存当前有活跃 run 的那个会话"，run 一结束就释放。**

### 改动点 1：给缓存加"生命周期"
- 缓存只在**一个 run 开始时**记录它所属的会话，在**这个 run 结束（完成/失败/中止）时**清除。
- 具体挂钩位置：
  - `markMessagesActive` / `unmarkMessagesActive`（现在已经有这对函数，用来标记"哪些消息正在被一个活跃 run 写入"）——把缓存的"该保留哪个会话"跟着这个活跃标记走。
  - run 结束的三个出口：`completeStreamingMessage`、`failStreamingMessage`、以及中止流程 `abortStreaming`——在这些地方释放缓存。

### 改动点 2：`updateCachedMessage` 不再全表扫描
现在它遍历"仓库里所有会话"去找一条消息（`chatStore.ts:204-215`）。
改成：只在"当前活跃 run 的那个会话"里找并更新。非活跃会话根本不进缓存，也就没得可扫。

### 改动点 3：流式写入不再无条件双写
`appendMessageDelta`（`:628-649`）等函数现在无条件写 `state.messages` + 写缓存。
改成：只有当"这条消息属于活跃 run 的会话"时才镜像进缓存；否则只更新 `state.messages`。
（正常情况下当前显示的会话 == 活跃 run 的会话，所以镜像该发生时依然会发生，切走切回不丢内容的保证不变。）

### 改动点 4：`reset()` 能真正清空
把 `messageCache` 的清理纳入 `reset()` 覆盖范围（`:693`），确保"重置聊天状态"时缓存也被清掉，不留残留。

> **不改的地方（重要）**：
> - 会话切换时"切走的会话存进缓存"这个入口（`selectConversation:267`）保留——但存进去的会话如果不是活跃 run，会在下次切换/reset 时被安全丢弃，不会常驻。
> - `selectConversation` 里合并 DB 与草稿的逻辑（含 #1 内容签名去重）**完全不动**。
> - `applyAgentEventToRun` 的 thinking/text 逻辑（#5）**完全不动**。

## 五、怎么验证没改坏（验收标准）

这是纯内部重构，必须证明"行为不变 + 问题消失"两件事。

**行为不变（回归）**：
1. 正常发消息、AI 流式回复，逐字显示正常。
2. AI 正在回复时，切到另一个会话，再切回来——**流式内容不丢**，继续显示。
3. 切换多个已完成的历史会话，消息显示正确、不重复、不丢失。
4. 编辑/重发消息（复用 id 的场景）行为正常。
5. `pnpm --filter desktop exec tsc --noEmit` 零类型错误。
6. `pnpm --filter desktop exec bun test` 相关测试通过（缓存/流式相关的单测若缺失则补上）。

**问题消失（证明修复有效）**：
7. 切换 N 个会话后，缓存里保留的会话数**不随 N 增长**（只保留活跃 run 会话，通常 0 或 1 个）——用一个单测断言 `messageCache.size` 上界。
8. 流式输出时，`updateCachedMessage` 不再遍历非活跃会话——用单测或临时插桩验证扫描范围。

## 六、风险与对抗性思考

| 风险 | 说明 | 应对 |
|------|------|------|
| 切走切回丢内容 | 收窄缓存后，万一"活跃会话"判定有误，可能丢流式内容 | 判定以现有的 `activeRunMessageIds` 为准（已被验证是可靠的活跃标记）；用验收项 2 专门测这个场景 |
| 并发多个 run | 若未来支持多会话同时跑，缓存需保留多个活跃会话 | 用"活跃会话集合"而非"单个活跃会话"，天然支持多 run；不写死为 1 个 |
| 我读代码时的误判 | 本方案基于对抗性复核后的结论（已证伪原 #4"闭包路由"误判） | 实现阶段每改一处，对照真实行号复核，不凭记忆 |
