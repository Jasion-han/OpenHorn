# 搜索来源与能力验证优化计划

**Goal:** 一个明确的当前搜索源；配置保存不承诺可用；只有用户显式验证成功后才启用新搜索源。

**Architecture:** 保留 Tavily、DeepSeek 和 DuckDuckGo 实际适配器，统一设置界面和服务端状态计算。DeepSeek 默认只填 Key、折叠中转地址，不再列出未经能力验证的聊天渠道。旧渠道配置保留读取和验证能力。验证通过真实搜索结果协议及来源检查，绑定当时的连接指纹；配置或来源在验证期间变化时拒绝迟到激活。

**Tech Stack:** React 19 / Radix / Hono / Bun / Drizzle / shared DTO。

**授权与取舍:** 用户已确认上一条回复中提出的优化方向并要求执行。采用本会话直接实施，不再次索取例行设计确认。不自动调用真实用户 Key 或收费接口；只在用户主动点击“验证并启用”时验证。自动化使用合成凭据与受控响应。保留现有浅色界面。

## Task 1：统一状态和显式验证

- [x] shared/types 定义搜索状态、激活请求/结果与结构化失败码。
- [x] DeepSeek 保存仅保存加密连接，不切换全局搜索源。
- [x] GET search-status 与运行时使用相同优先级，区分配置存在与验证状态。
- [x] POST 验证并启用：仅已保存配置，受控次数/超时、失败保留原搜索源，成功原子写入来源与验证指纹。
- [x] 验证期间配置/凭据/来源变化拒绝激活；不返回上游敏感错误。
- [x] Bun 覆盖成功、失败、协议不兼容、配置变化、回滚、用户隔离。

## Review Focus

- 配置保存成功但能力未验证时，不能显示已启用。
- DeepSeek 验证失败不能让原有 Tavily 失效，也不能静默替换搜索引擎。
- 中转地址/Key 和旧渠道凭据变化后不能沿用旧验证标记。
- 迟到验证不能覆盖另一个窗口刚切换的来源。
- 当前有效状态来自服务端，不根据表单选择或客户端猜测。
