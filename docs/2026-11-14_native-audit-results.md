## 代码结构与文章借鉴落点

这是 Tauri/React 桌面、Bun Sidecar 与 Hono 服务端组成的工作区。桌面不是简单地直接向模型发请求：本地操作、上下文准备、流式执行和持久化由不同进程承担，改动必须覆盖整条链路。

| 模块 | 实际职责与入口 | 本次借鉴与边界 |
|---|---|---|
| 桌面外壳与导航 | `App.tsx`、`DesktopShellLayout`、`DesktopLeftSidebar`；Chat、Library、Workbench、Scheduled Tasks、Settings | 保留已有工作区结构；新能力进入已有入口，不增加第二套应用壳 |
| 桌面 Chat | `chatStore`、`serverApi`、`sidecarClient`、流式 Markdown/消息操作栏 | 把原生联网过程、引用、失败/拒答/停止状态接入现有消息，不只在设置里加开关 |
| 桌面 Agent | `useSidecarAgentRun`、`sidecarRunSupport`、Agent 执行面板 | 与普通 Chat 分开；本轮实际跑通文件工具与快照回滚，保持权限确认语义 |
| 服务端 Chat | `messageService` 与 `/messages`；prepare/complete 与 SSE send/edit/regenerate | 对私有 provider state 做身份隔离；新客户端使用 saveToken 拒绝迟到回写 |
| 协议适配 | `packages/adapters`；OpenAI、Anthropic、Google 与 DeepSeek 原生网页扩展 | 可选事件回调扩展原来的文本 generator；不向其他网关注入 DeepSeek 私有参数 |
| 共用外部检索 | `packages/shared/src/search` | Search/Fetch 协议、安全 URL、归一化来源与 provider 选择由两端复用 |
| 资料库 | `/library`、`libraryService`、`libraryOcr`、LibraryView | 沿用原件、租约与本地索引；云端 OCR 独立确认、按页提示，不在普通上传中隐式触发 |
| 数据迁移 | `/data-transfer`、DeepSeek 导入模块、BackupFileImportRow | 按真实归档内容识别、稳定去重、事务导入；本轮补齐失败码与中文处理建议 |
| 工具配置 | `/settings`、`/mcp`、SettingsView 的 Agent/MCP/Skill 页 | 工具 Key 与模型 Key 分开；非法配置在前后端均拒绝；配置名保留为自有字典键 |
| 存储 | `packages/db` schema、server bootstrap、原件与快照目录 | 双份 schema 同步；模型回传 state 与展示 metadata 分离；快照不写进用户项目 |
| 工作台与定时任务 | recipes/artifacts/review/scheduled 模块 | 保留现有职责；此次没有借文章扩成新调度系统，也没有声称逐项原生验证过 |

采用的是“共用独立工具 + 显式 provider 原生模式”。这让其他模型可以复用检索能力，同时保留 DeepSeek 原生引用和网页上下文。语音 ASR/TTS、Files 图文混排仍后置。真实 DeepSeek 付费能力的效果与账单行为，本轮没有实测。

普通桌面 Chat 的关键顺序为：

```text
React → server prepare（有效策略、历史、saveToken）
      → 本机 Sidecar → provider adapter（文本与独立 metadata）
      → React → server complete（快照校验与持久化）
```

Agent 则走 Sidecar 的文件/工具循环。其运行结束后发布 `checkpoint.ready`，回滚 RPC 同时校验 runId 归属与最初工作区。

## 发现、修复与证据

### 1. 模型使用绝对路径后，改写成功却没有回滚快照

真实模型读取 `qa.txt` 后使用工作区内绝对路径调用 `write_file`，文件已改变，但没有 `checkpoint.ready`。检查实际事件后定位到 `direct.ts`：文件工具接受绝对路径，快照函数却只接受相对路径；备份错误被既有 best-effort 逻辑忽略。

在调用快照备份前，使用快照所属工作区把路径转换为相对路径，与 Claude 路径已有处理一致。没有放宽工作区或快照目录的安全校验。

证据链：真实模型事件发现 → `direct.checkpoint.test.ts` 对 write/edit 均红测 → 最小路径转换 → 两项测试通过 → 重新编译 Sidecar → 真实模型改写、发布快照、回滚并逐字比较原文通过。

默认权限下模型曾先要求确认修改；测试按产品语义提供明确确认后继续，没有把正常确认行为改成自动绕过权限。

### 2. Office/图片提供无法完成的“本地重建”操作

原 `canIndex` 只判断租约，没有判断本地解析能力。实际 SQLite/HTTP 复现中，Office 和图片均返回 `canIndex=true`，点本地重建只会再次返回“需要云端解析”。

现在只有文本和 PDF 在可领取租约时提供本地重建；云端支持格式继续独立计算 `canOcr`。扫描 PDF 仍可本地重试并提供显式 OCR。有效占用期间两者禁用，租约过期按格式恢复能力。OCR ready 的文档不开放重复收费入口。

证据：`libraryCapabilities.test.ts`/fixture 的 199 项断言，以及新后端上的 DOCX、PNG、文本实际上传/查询/下载。没有发出真实 OCR 请求。

### 3. 导入失败只展示原始错误，用户不知道怎样处理

导入检测与执行现在返回共享 `DataTransferImportErrorCode`，同时保留旧 `error` 字段。覆盖参数缺失、文件不存在/不可读、归档损坏、识别不匹配、不支持格式、连接失败与一般失败。

`serverApi` 保留结构化错误，BackupFileImportRow 通过字典给出对应中文提示。例如文件已移动时提示重新选择，不再把底层错误直接显示给用户。没有按错误字符串猜测翻译；部分成功、验证失败和中断的正常导入结果保持原契约。

证据：真实临时 SQLite/loopback HTTP + 实际客户端 transport 测试、8 个字典 key 的映射与非空校验，以及新后端上的实际错误请求。

### 4. 无效 MCP 配置被保存，特殊设置键消失

实际请求曾证明：`config:null` 创建 MCP 返回成功，但列表悄悄把它变成空对象；保存 `__proto__` 设置后读取则丢失。

MCP create/update 现在在写入前要求 JSON 对象，拒绝 null、数组、标量及缺失的 create config；返回 `mcp_invalid_config` 并保留旧错误。更新先核验归属，继续保留外用户 404。界面 create/edit 也在发请求前拒绝非对象，toggle-only 与空对象更新仍可用。

设置读取与启用的 MCP 名称映射使用无原型字典，`__proto__`、`constructor`、`toString` 可完整保存、读取和经过 RPC 序列化。没有执行测试 MCP 命令，也没有连接真实 MCP 服务。

证据：真实 SQLite/HTTP 验证写入前后数据库不变、归属、切换与特殊键；客户端 roster 与真实组件 handler 测试。本轮没有看到 MCP 原生弹窗，handler 测试不能证明其视觉状态。

真实 Sidecar 完整复验的七组结果：

1. 启动编译后的可执行文件并通过随机 token 握手。
2. 读取实际工作区文件，拒绝路径越界。
3. prepare → 真实 provider → complete → HTTP 重载，正文一致。
4. 实际 SSE retry 替换回答，重载后仍一致。
5. retry 后拒绝旧 prepare 的迟到完成，HTTP 409。
6. 首段文本到达后实际 cancel，精确 partial 以 stopped 保存。
7. 提供明确修改授权后，实际 Agent read/write，发布快照并回滚原文。

第一轮在上述前六项后因 Agent 检查失败而以失败结束；报告没有把该轮写作全通过。修复后对完整七组重新执行，最终整体通过。

QA 后端使用独立端口、独立 SQLite/上传目录和新生成的本地加密配置。仅复用已有用户渠道凭据来调用既有默认模型，没有复制用户会话，没有输出或提交密钥。原本运行的应用及 3002 后端保持原样；其进程没有加载本轮新路由，不能因网页/源码变化就假定已自动升级。

## 尚未关闭的范围与运行时限制

- **原生窗口与系统控件**：目前没有逐步看到文件选择器、系统打开链接、窗口拖动/缩放、原生快捷键、重启恢复和展开控件状态。必须解锁后继续下一节，不能仅凭构建通过关闭。
- **DeepSeek 真实付费请求**：本轮真实 provider 验证使用已有默认模型；DeepSeek Search/Fetch、原生联网、OCR 的真实质量、配额和计费未验证。之前的协议回放与本轮本地合同测试保留各自边界。
- **Bun 1.3.10 小型 multipart 缺陷**：独立于 Hono/业务路由的 Bun HTTP 探针中，部分 6–8 字节且含 NUL 的合成文件完整进入 HTTP body，但 `request.formData()` 解析后截为 4 字节。真实 783 字节 DOCX、68 字节 PNG、文本的上传下载 SHA-256 一致。该边界问题未修复，不能宣称任意二进制输入的原件完整性已全面通过；未为其引入手写 multipart 解析器。
- **构建体积**：Vite 仍报告大于 500 kB 的 chunk 提示。构建成功；未在缺少原生性能测量时盲目调整切包策略。
